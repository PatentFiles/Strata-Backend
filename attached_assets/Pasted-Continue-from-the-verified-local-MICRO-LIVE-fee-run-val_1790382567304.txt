2. Define precedence explicitly

Fee evaluation must use:

1. any applicable market/event-specific override if Kalshi exposes one,

3. the approved formula artifact only to interpret that fee type/formula.

If any required layer is unknown, contradictory, stale, unsupported, or cannot be parsed, block submission.

3. Handle scheduled fee changes

Before entry or exit eligibility, check whether a scheduled fee change exists for the relevant series.

If a change becomes effective before the order could be submitted or while a reserved live lifecycle remains open, recompute the complete fee-inclusive worst-case debit. If the exact $5 cap can no longer be proven, block.

4. Make invalidation durable

Replace the process-local fee invalidation latch with transactional database-backed state.

Any observed:

* authoritative artifact mismatch,
* unsupported fee type,
* contradictory fee metadata,
* unprovable applicability,
* failed required verification,

must commit a durable blocked state before the process may continue.

After restart, the system must read that state before any execution eligibility check.

A successful later fetch must not silently clear a durable invalidation. Clearing it must require the already-defined explicit administrator review/reapproval path.

5. Keep source outages distinct

A temporary PDF HTTP 429 should not be interpreted as evidence that the fee schedule changed.

It should:

* block any action that truly requires fresh PDF verification,
* record source unavailable,
* preserve the last approved artifact hash,
* never substitute cached content as newly fetched evidence.

Since runtime fee applicability should now be proven through the live Kalshi fee metadata, PDF rate limiting should no longer by itself prevent continuous operation when the approved artifact is already established and unchanged.
