ARCHITECTURE

The browser must no longer be responsible for keeping the forward test alive.

Create ONE authoritative server-side worker that:

1. Runs independently of any browser session.
2. Polls the required Coinbase and Kalshi market data.
3. Builds the exact same strategy input currently used by V1.3.
4. Calls the existing authoritative evaluateV13Strategy function.
5. Does NOT implement a second copy of the strategy rules.
6. Persists evaluations, windows, crossings, positions, and settlements into the existing Phase 2 PostgreSQL tables.
7. Restores state from PostgreSQL after restart.
8. Continues the same forward-test ledger after restart.
9. Uses database-level duplicate protection already built in Phase 2.

CRITICAL SINGLETON PROTECTION

The deployment may run more than one server process or restart unexpectedly.

The worker MUST NOT rely on JavaScript process memory to guarantee one active engine.

Implement a PostgreSQL-backed worker lease / leader lock.

Requirements:
- only one worker may own the V1.3 engine at a time
- lease has an owner ID
- lease has acquired/renewed timestamps
- lease expires if the owning process dies
- another worker may safely acquire it after expiration
- heartbeat renews the lease
- every evaluation verifies that this process still owns the lease
- loss of lease immediately stops evaluation/writes
- database constraints remain the final duplicate-action defense

Do not use an in-memory-only lock.

SERVER LOOP

Use a conservative recurring loop appropriate for the existing market polling cadence.

Each cycle should:

A. Confirm worker lease
B. Fetch current Coinbase market data
C. Fetch current Kalshi 15-minute market data
D. Validate data freshness
E. Determine/currently restore the active 15-minute market window
F. Persist the market snapshot/window state
G. Run evaluateV13Strategy with the same inputs used by the browser implementation
H. Persist the strategy evaluation
I. Atomically claim any qualifying fresh crossing
J. If Scout/Confirm qualifies, create/update the PAPER position only
K. If an existing paper position qualifies for exit or settlement, process it exactly once
L. Persist results
M. Update worker heartbeat/status
N. Record any error without corrupting engine state

FAIL CLOSED

If any required data is:
- unavailable
- malformed
- stale
- inconsistent
- missing target
- missing offer
- from the wrong market/window

the server worker must NOT create a paper position.

Record the evaluation/error state and continue on a later cycle.

Do not invent substitute market values.

RESTART RECOVERY

On worker startup:

1. Read forward_test_engine.
2. Read current/open forward_test_window.
3. Read any open forward_test_position.
4. Read previously consumed crossings/actions.
5. Recover the last successful evaluation.
6. Resume without treating old crossings as new.
7. Never duplicate a Scout, Confirm, exit, or settlement because of restart.
