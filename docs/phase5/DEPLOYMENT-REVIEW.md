## Ambiguous submission: no-duplicate recovery

An HTTP timeout, malformed response, or crash after POST may have created an exchange order even when the local row has no `exchange_order_id`. The order has a persistent unique `action_key` and `client_order_id`. Startup deliberately returns `reserved_submission_missing_exchange_id` and refuses readiness for an ID-less pending/unknown order. **Never re-POST, delete the reservation, zero its risk, mark it rejected from a timeout, or assume “not in resting orders” means “not submitted.”** Both entry and EXIT can have partial/terminal fills.

1. Freeze: emergency stop, both environment flags false, kill switch ON; prevent competing workers and preserve the local order, decision, evaluation, timestamps, client order ID, and any error evidence. Do not send a cancel/new order while identity is uncertain.
2. The admin-only `POST /api/micro-live/reconcile-uncertain` accepts `{ "orderId": "<local UUID>" }`. It requires **both environment flags OFF, both database flags OFF, and the kill switch ON**. It performs only signed exchange GETs: complete paginated current and historical *orders*, current and historical *fills* where offered, plus the account snapshot. Current resting orders alone are not enough. The exchange may return an empty client ID on unrelated orders; only the exact stored `client_order_id` may match.
3. If **exactly one** exchange order has the stored client ID, the workflow verifies ticker, side, buy/sell action, limit, original size, exchange fill count, individual fill identity/price/quantity and authenticated source provenance. A historical-only fill may now be linked when it appears in the complete `/historical/fills` GET with a matching identity, and the combined evidence sums to the order's authoritative `fill_count_fp`. Normal startup must independently re-read that ticker's historical fills, require the authenticated per-order GET's filled count for **every order status (including canceled partials)**, and reconcile the deduplicated fill sum, account positions and order totals before readiness. A 404 from `/historical/fills` is **not** evidence of zero fills: current fills must alone establish the full order total or execution remains blocked. Any conflicting overlap, foreign fill, unavailable needed history, or truncated page blocks. It checks no other local order owns the exchange ID, then atomically binds that ID to the **existing** reservation and writes an audit decision with the admin identity and a SHA-256 digest of the matched evidence.
4. The bound reservation stays `unknown` with its full reserved risk and kill switch ON. The endpoint **never** marks it rejected, reposts it, clears its risk, creates a second local order, or enables execution. A second call cannot relink the order. If no unique match is found, history is truncated, evidence conflicts, or an exchange GET fails, it records a blocked decision for an eligible local row and leaves the submission unresolved.
5. **Unknown-ID sell EXIT, separately from read-only linking:** the administrator may explicitly request `POST /api/micro-live/recover-and-cancel-uncertain-exit` with the local exit UUID while both environment/database execution flags are OFF and the kill switch is ON. This separate path reads complete signed ticker-scoped order/fill evidence and account snapshot, proves exactly one matching client/order identity, ticker, side/action, original limit/count, authoritative filled count and every identified fill, and transactionally binds or re-verifies that ID without releasing risk. It then calls the existing identified-order cancel-and-verify routine, which first freezes execution and independently requires complete *account-wide* history, verified exclusive control, and a fresh exact-order status. Before any DELETE, a database-row-locked, durable single-use cancellation claim is written; concurrent or restarted requests cannot issue a second DELETE. A failed or unknown response or a crash leaves the claim and risk frozen, never automatically retried. A 409 is a frozen, unresolved attempt, **not** proof of cancellation. The old `/reconcile-uncertain` path remains link-only and never cancels. Do not try a second EXIT or POST either way.
6. **Only in a separately approved maintenance window:** ensure no trading worker or competing process can submit, then run normal full startup reconciliation with the required gates temporarily eligible; inspect order/fill/position/balance consistency and the process-local readiness result *before* any worker can run. Startup reconciliation does not run while environment gates are off. If any discrepancy appears, re-freeze and do not activate. These development tests do not prove a future production maintenance window is safe. A recovered unknown must never cause a second POST for its original action.

## Count each charge once: the $1 budget and the selected market

**Policy versus measurement.** The newly applied development source package explicitly **changes the pre-POST $1 gate from quantity 3 to quantity 1 plus any additional negative net cash change on a permitted exit**. This also bounds loss for an isolated simple YES/NO position under the verified fee and settlement assumptions, because nonnegative sale or settlement credits can only reduce loss. The numeric cap stays **1,000,000 micro-dollars**; this is a change in what it measures, not an increase in the number. The live path uses `withinAllInLiveTestCap`, while the older entry-only `withinLiveTestCap` remains a separate helper. The previous entry-plus-withheld-gross-proceeds gate is not still active. Existing order fingerprints and durable attempted reservations are not reset. The live path must freshly verify the selected market/series/event and approved schedule; an expired market snapshot never authorizes a later market. This development patch is **not approval to publish or trade**.
