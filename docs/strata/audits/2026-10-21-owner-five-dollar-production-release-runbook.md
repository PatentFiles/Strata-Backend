## Provider contract correction: direct test and UNKNOWN recovery
Kalshi's current official `POST /portfolio/subaccounts/transfer` returns **an empty JSON object**, while `GET /portfolio/subaccounts/transfers` returns a **transfer_id**, not the submitted client_transfer_id. Legacy #133 compared an undocumented field and would permanently block successfully funded balances. Instead, the corrected code issues one fixed-scope `POST /portfolio/intra_exchange_instance_transfer` for the bot leg (primary0/shard2 → subaccount1/shard2) and captures the returned server-assigned `transfer_id`. Same-shard intra-account transfers are treated as subaccount transfers per Kalshi docs. The shard0→shard2 leg still uses a client_transfer_id (valid on primary-account transfers); numbered bot legs omit this key because Kalshi rejects it for numbered subaccounts. The database claim remains **one-use** before any POST. Provider-shard receipts must echo the client ID; bot receipts must match the server-issued `transfer_id`, exact 0→1 subaccounts, index 2, exact cents and narrow timestamp window, with complete pagination, no duplicates, and exact signed before/after cash. Both require fresh signed zero-exposure proofs before ledger credit.

A timeout/crash before receiving the server-issued `transfer_id` remains `claimed/uncertain` and **cannot** automatically be repaired as success by guessing from one matching balance movement. Obtain independent provider evidence and operator-reviewed recovery or preserve the account maintenance hold; NEVER issue a second POST. This is a deliberate safe limitation.
